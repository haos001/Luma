# Как опубликовать репозиторий

Папка подготовлена как самостоятельный проект. Репозиторий: [haos001/Luma](https://github.com/haos001/Luma). Готовые сборки предназначены для [Releases](https://github.com/haos001/Luma/releases), а не для истории исходников.

## Перед первым push

1. Просмотрите `README.md`, `README.ru.md` и `LICENSE`. Лицензия — MIT; уведомление об авторстве: `2026 Luma contributors`. При желании укажите своё публичное имя в уведомлении **до публикации**.
2. Проверьте публичное имя и email автора коммитов: `git var GIT_AUTHOR_IDENT`. Для приватности можно использовать свой GitHub noreply-email. Не вставляйте токены в URL remote.
3. Включите на GitHub private vulnerability reporting либо добавьте свой проверенный контакт в `SECURITY.md`.
4. Проверьте `git remote -v`: для этого проекта `origin` должен указывать на `https://github.com/haos001/Luma.git`. Если публикуете собственный форк, используйте адрес своего репозитория.
5. Выполните `git status --short`, просмотрите изменения и при необходимости создайте коммит. Используйте существующую историю `main`, не перезаписывайте её force-push.
6. После авторизации в GitHub выполните `git push -u origin main`.

Не добавляйте токены в URL remote и не сохраняйте их в файлах проекта. Для нового компьютера настройте поддерживаемую GitHub авторизацию отдельно.

## Оформление GitHub

Рекомендуемое краткое описание:

> Native macOS ambient-light controller for a tested ROBOBLOQ USB backlight. Pick a color, quit the app, keep the light.

Подходящие topics: `macos`, `swift`, `swiftui`, `usb-hid`, `ambient-lighting`, `rgb`, `iokit`, `native-app`.

В README уже есть локальная векторная обложка, русская версия, быстрый старт и описание ограничений. Значок успешного CI лучше добавить только после первой реально прошедшей сборки и появления адреса репозитория.

## Что не публиковать

- `.build/`, `dist/`, локальные `.app`, логи и временные файлы в истории исходников.
- Настройки из `~/Library/Application Support/`.
- `.env`, сертификаты, ключи Apple Developer, пароли и токены.
- Старое стороннее приложение, его ресурсы или прошивку устройства.

`.gitignore` защищает типичные пути, но не заменяет просмотр содержимого коммита. Исходный архив можно использовать для передачи проекта; готовые бинарники следует прикладывать отдельно к релизу.

## Первый релиз с готовым приложением

1. Соберите ZIP: `bash scripts/build.sh`, затем `bash scripts/package-release.sh`.
2. В репозитории GitHub откройте **Releases → Draft a new release** и подготовьте тег `v0.4.0` на проверенном коммите.
3. Возьмите заголовок и описание из [готового черновика релиза](releases/v0.4.0.md).
4. Прикрепите ZIP из `dist/releases/` и соответствующий `.zip.sha256`. При наличии приложите также отдельный архив исходников и его checksum, указанные в черновике.
5. Замените уведомления о подготовке релиза в README и инструкциях настоящими ссылками. Проверьте список файлов, ограничения совместимости и предупреждение об отсутствии нотарификации.
6. Опубликуйте проверенный релиз. После загрузки скачайте ZIP обратно и проверьте контрольную сумму.

Бинарники не нужно коммитить в исходники. Артефакты вкладки Actions предназначены для разработки и могут истечь; готовое приложение для пользователей должно лежать в **Releases**. Автоматические ссылки GitHub «Source code» — это исходники, а не приложение.

Подробный [чек-лист релиза](RELEASING.md) отдельно описывает ручные проверки. CI не публикует релизы автоматически.
